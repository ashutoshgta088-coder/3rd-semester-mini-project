02 • RECAP
Project Recap (from Review-01)
Foundation & Objectives

⚠️ The Academic Problem

  • Time Wastage: Manual roll-calls consume 10–15 minutes of every 50-minute lecture (20–30% lecture overhead).
  • Proxy Attendance: Paper signature sheets and static QR codes shared via WhatsApp enable rampant off-campus proxy submissions.
  • Data Tampering: Physical registers suffer from accidental misplacement, physical wear, and error-prone manual Excel aggregation.
  • Delayed Interventions: Lack of real-time attendance analytics prevents timely alerts for students below the mandatory 75% AKTU threshold.

🎯 Core Project Objectives

  • Zero-Hardware Proximity Verification: Use standard Bluetooth Low Energy (BLE) advertisements from faculty smartphones to define classroom boundaries.
  • Multi-Factor Anti-Proxy Verification: Require student device token, rotating 30s session passcode, and optional WebAuthn passkey.
  • Real-Time Live Dashboard: Instant display of verified attendance records on the teacher's dashboard without manual page refreshes.
  • Institutional Compliance: Native support for AKTU 13-digit roll numbers, semester/branch filtering, and 1-click Excel export.

04 • ARCHITECTURE
System Architecture & End-to-End Workflow
Full-Stack BLE Workflow

🔄 Workflow Stages

  1. Session Creation: Teacher initiates session (Subject, Branch, Duration). Server generates unique Session ID & dynamic Passcode.
  2. Classroom Advertising: Teacher phone broadcasts temporary BLE beacon identifier or displays dynamic OTP.
  3. Student Discovery: Student scans nearby BLE signals or discovers active session via authenticated dashboard.
  4. Verification & Submission: Student submits payload (Roll No, Passcode, Device Token, GPS).
  5. Validation & Real-Time Sync: Backend checks expiry, duplicates, and proximity, updates MongoDB, and reflects on Teacher's live roster.

05 • IMPLEMENTATION
Implementation Details & Anti-Proxy Defense
Multi-Layered Security

🛡️ Layer 1: BLE Proximity

Bluetooth Low Energy RSSI thresholds (-70 dBm) ensure the student device is physically inside the lecture hall (within 5–10 meters).

Prevents remote off-campus proxy submissions.

⏱️ Layer 2: Rotating Passcode

Dynamic 6-character room passcode rotates every 30 seconds via HMAC-SHA256 time-based algorithm.

Screenshotted codes expire before students can forward them.

📱 Layer 3: Device Binding

Student accounts bind to a unique hardware fingerprint. Backend enforces strict 1 Student : 1 Device per session policy.

Eliminates marking attendance for absent friends.

⚡ Real-Time Attendance Engine

MongoDB compound unique index on (sessionId, studentId) guarantees mathematical zero-duplicate submissions at the database engine level, rejecting race conditions within 4 milliseconds.

09 • CONCLUSION
Conclusion, Challenges & Future Scope
Summary & Roadmap

💡 Key Challenges & Solutions

  • Challenge: Bluetooth disabled on student devices.
    Solution: Automatic fallback to dynamic 30s rotating classroom passcode.
  • Challenge: Multiple devices submitting at the same exact millisecond.
    Solution: MongoDB compound unique indexes to guarantee idempotency.
  • Challenge: Render cloud deployment with isolated subdirectories.
    Solution: Unified build script syncing React dist into Express public root.

🔮 Future Enhancements

  • Hardware ESP32 Beacons: Permanent solar/USB BLE beacons installed inside classrooms.
  • Facial Verification with Anti-Spoofing: On-device TensorFlow.js 3D depth verification.
  • Direct ERP Synchronization: Automated REST webhooks into university AKTU ERP portals.
  • Offline Peer-to-Peer Mesh: Bluetooth mesh relaying attendance even when campus Wi-Fi drops.
